# Отчёт по практической №1

## 1. Вариант и масштаб

| Поле | Значение |
| :---- | :---- |
| ФИО (как в VK Education) | Кряжев Дмитрий |
| Вариант (запрос) | Q16 |
| Масштаб `sfN` | sf1 |
| Почему выбрал такой масштаб | sf1 даёт около 800 тыс. строк в `partsupp`: этого достаточно для показательного бенчмарка, но запрос выполняется за секунды и не требует десятков ГБ диска. TPC-H детерминирован, поэтому результаты воспроизводимы. |

&nbsp;

## 2. Поднятые сервисы — и почему именно они

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
| :---- | :---- | :---- |
| MinIO | S3-совместимое объектное хранилище: в нём физически лежат parquet-файлы | Лёгкий локальный S3-совместимый сервис. Позволяет отделить хранение от вычислений и не разворачивать тяжёлый HDFS. |
| PostgreSQL | БД, в которой Lakekeeper хранит метаданные каталога | Проверенная реляционная СУБД, простая в эксплуатации и достаточная для хранения метаданных Iceberg-каталога. |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | Даёт ACID, снапшоты, time travel и schema evolution. REST-интерфейс позволяет разным движкам работать с одним каталогом. |
| Trino | SQL-движок: получает метаданные из Lakekeeper и читает/пишет данные в MinIO | Быстрый распределённый SQL-движок с нативной поддержкой Iceberg и REST-каталогов. Удобен для ad-hoc аналитики. |
| (BI: Superset / Metabase) | Отчёты и дашборды поверх Gold-слоя | BI-слой проверяет, что витрины доступны не только SQL-движку, но и внешним аналитическим инструментам. |

## 3. Разбор запроса — какие данные нужны

Ниже перечислены таблицы и колонки TPC-H, которые действительно участвуют в Q16.

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
| :---- | :---- | :---- |
| part | partkey, brand, type, size | фильтрация по brand/type/size, соединение по partkey |
| partsupp | partkey, suppkey | соединение с part, участие в count(DISTINCT suppkey) |
| supplier | suppkey, comment | подзапрос: отсеивает поставщиков с жалобами |

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
| :---- | :---- |
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Классическая БД плохо масштабируется до петабайт и обходится дорого. Lakehouse сочетает дешёвое объектное хранение (S3), ACID-транзакции, открытые форматы (Iceberg/Parquet) и SQL-доступ. Один и тот же набор данных могут читать разные движки — Trino, Spark и другие. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | В Iceberg можно выполнить `ALTER TABLE silver.q16.enriched_partsupp ADD COLUMN new_col int`: метаданные обновятся атомарно, старые parquet-файлы перезаписывать не нужно. Для строк, записанных ранее, новый столбец будет читаться как NULL. |
| Пример скрипта восстановления данных из снапшота (time travel) | `SELECT * FROM gold.q16.supplier_count FOR VERSION AS OF <snapshot_id>;` — так можно откатить ошибочный DELETE или посмотреть, как витрина выглядела вчера. |

&nbsp;

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
| :---- | :---- |
| Metabase | Открытый BI-инструмент, подключается к Trino по JDBC, запускается одной Docker-командой и позволяет строить графики без кода. Он находится в той же сети `lakehouse-net`, что и Trino, и видит Iceberg-таблицы через Trino. Это подтверждает, что данные Lakehouse доступны не только SQL-движку, но и BI-слою. |

&nbsp;

```sh

# Открыл http://localhost:3000 и прошёл мастер настройки.
# Settings → Admin → Databases → Add Database.
# Тип: Starburst (Trino), Хост: trino, Порт: 8080, Catalog: bronze, Schema: q16, User: trino, Password: пусто.
# После сохранения нажал «Синхронизировать схему» — Metabase увидел таблицы raw_part, raw_partsupp, raw_supplier.
# Построил график: New → Question → raw_part → Summarize → Group by: brand, Metric: Count of rows → Bar Chart.
```

## 7. Выводы

В ходе практики я развернул локальный Lakehouse (MinIO + Lakekeeper + Trino) и собрал полный медальонный пайплайн Bronze → Silver → Gold для запроса Q16 (TPC-H) на масштабе sf1. В Bronze сохранены три сырые таблицы (`part`, `partsupp`, `supplier`). В Silver отфильтрованы поставщики с жалобами и выполнен join `part`↔`partsupp`. В Gold сформирована компактная витрина `supplier_count` (~300 строк, 40 КБ), которая отвечает на исходный вопрос Q16 и сходится с эталоном. Бенчмарк сжатия показал, что ZSTD читается почти в 2 раза быстрее GZIP (0.125 с против 0.215 с), хотя на маленьких файлах GZIP может дать чуть меньший размер; для продакшена предпочтительнее ZSTD. Дополнительно к Lakehouse был подключён BI-инструмент Metabase: через Trino он читает Bronze-таблицы и строит визуализации. Это доказывает, что архитектура открыта и не привязана к одному движку. Главный вывод: медальон + Iceberg + открытые форматы дают гибкость, дешёвое хранение и возможность аналитики разными инструментами.
